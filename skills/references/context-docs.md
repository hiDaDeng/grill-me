# 领域上下文文档

使用 `CONTEXT.md` 固定领域语言，使用 `CONTEXT-MAP.md` 描述多个上下文及其关系。它们服务于概念一致性，不承担规格、计划或实现记录。

## 发现结构

1. 根目录存在 `CONTEXT-MAP.md`：按地图定位当前主题所属的上下文及其 `CONTEXT.md`。
2. 只有根目录 `CONTEXT.md`：视为单上下文项目。
3. 两者都不存在：只在首个项目特有术语已经锁定且用户启用活文档维护时，使用 [context-template.md](../assets/context-template.md) 惰性创建根目录 `CONTEXT.md`。
4. 多上下文归属不明确时先询问；不要把一个术语同时写入多个上下文。

## 记录规则

- 把 `CONTEXT.md` 保持为词汇表。规格、任务、API、数据库字段和实现决定分别进入其所属文档。
- 为一个概念选择一个标准术语，把容易混用的名称列入 `_避免_`。
- 每个定义限制为一至两句话，说明概念是什么及其边界，不罗列实现行为。
- 只记录项目领域特有概念。超时、错误类型、工具函数等通用工程词汇不进入词汇表。
- 自然形成多个概念簇时使用小标题；单一领域保持扁平列表。
- 新术语与现有定义冲突时立即指出，用具体场景确定哪个含义成立。
- 用户描述与代码行为冲突时展示证据并要求裁决；在裁决前不改写文档或代码。

## 多上下文地图

确定项目确有多个独立领域上下文后，使用 [context-map-template.md](../assets/context-map-template.md)。地图只记录：

- 每个上下文的职责与文档位置；
- 上下文之间的通信方向与方式；
- 明确共享的类型或契约；
- 关键所有权边界。

关系或边界发生难逆转的架构取舍时，另按 [adr-docs.md](adr-docs.md) 判断是否建立 ADR。

## 写回时机

活文档维护模式下，每批问题结束后写回本批已经锁定的术语。保留原有有效内容和结构；不要为了套模板重排整份文档。写回后检查标准术语是否也用于最终锁定方案。
