# 架构决策记录

ADR 记录“做了什么重要决定，以及为什么”。它不是会议纪要、任务清单或完整设计文档。

## 建立门槛

只有以下三项同时成立才建立 ADR：

1. **难以逆转**：以后更改需要明显迁移、协调或替换成本。
2. **缺少背景会令人困惑**：未来维护者仅看代码很可能误解或尝试“修正”这个选择。
3. **存在真实取舍**：至少有一个可信替代方案，并因具体理由被放弃。

任一项不成立就不建 ADR。可逆实现细节留在计划、规格、代码或提交记录中。

## 常见对象

- 架构形态和上下文边界；
- 跨上下文集成方式；
- 带明显锁定成本的数据库、消息系统、认证或部署选择；
- 数据所有权和明确的范围排除；
- 有意偏离常规方案的选择；
- 代码中看不见的合规、性能或外部契约约束；
- 理由不明显、以后很可能被再次提出的被拒方案。

## 文件与编号

- 系统级 ADR 放在根目录 `docs/adr/`；已有上下文级惯例时遵循该惯例。
- 首次需要时再创建目录。
- 扫描现有文件的最高四位编号并加一，命名为 `NNNN-short-slug.md`。
- 不重用废弃 ADR 的编号；改变旧决定时新建 ADR，并在状态中标记取代关系。

## 内容

默认使用 [adr-template.md](../assets/adr-template.md)，用一至三句话写清背景、决定和理由。以下部分仅在确有价值时添加：

- `状态`：拟议、已接受、已废弃、被 ADR-NNNN 取代；
- `考虑过的方案`：被拒方案及拒绝理由值得未来保留；
- `后果`：存在不明显的下游影响或维护成本。

活文档维护模式下，等取舍明确并获得用户确认后再写入。写入后从锁定方案链接该 ADR，并检查方案使用的术语与对应 `CONTEXT.md` 一致。
